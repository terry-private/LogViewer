# ログの保持上限と画面キャッシュ

## 背景

ログを無制限に保持すると、長時間起動するアプリでメモリ使用量が増え続ける。
また、配列の先頭削除、ログ本体の複数索引への重複保持、SwiftUIの表示評価ごとの
検索・絞り込み、行ごとの`DateFormatter`生成が、大量ログ時の応答性を悪化させる。

## 決定

標準の`InMemoryLogStore`は最新1万件を保持する。
`maximumEntryCount`で0以上の上限を初期化時に指定できる。
上限を超えた場合は記録日時ではなく追加順を基準に、先に追加されたログから
決定的に削除する。

保存配列には`swift-collections`の`Deque`を使い、先頭削除を定数時間で行う。
変更通知の購読者がいない場合は、追加のたびにSnapshot配列を生成しない。

画面はSnapshotを正本とし、Snapshotまたは絞り込み条件が変わった時だけ、
次の派生情報を再構築する。

- 重複を除いたタグと発生元の表示順
- 絞り込み済みログの単一配列
- ファイル別・関数別グループが参照する配列添字

グループ索引にはログ本体を複製しない。
日時表示用の`DateFormatter`はMainActor上で1つだけ生成して共有する。
1万件の検索キャッシュ再構築は、シミュレータ上で1秒以内を基準とする。

## 採用理由

- 標準利用でもメモリ使用量に明確な上限を設けられる
- 追加順という保存機能自身が管理する順序で、削除結果が安定する
- 公開済みの`LogStore`契約を変更せず、別の保存実装へ差し替えられる
- 表示評価のたびに全件検索と全索引生成を繰り返さない
- ログ本体の三重保持を避けられる

## 採用しなかった方式

- 記録日時が古いログから削除する方式:
  遅れて届いたログや同一日時の扱いが追加順と一致せず、保存処理が複雑になるため
  採用しない。
- 通常の`Array.removeFirst`を使う方式:
  上限到達後の追加ごとに要素移動が発生するため採用しない。
- ファイル別・関数別に`LogEntry`配列を保持する方式:
  同じ値を複数箇所へ保持し、削除時の整合性管理も必要になるため採用しない。
- 無制限を標準に残す方式:
  利用側が設定を忘れた場合に長時間起動の安全性を保証できないため採用しない。

## 影響

- `Logger.shared`を含む標準保存先は、1万件を超えた古いログを自動削除する
- 大きな上限が必要な利用側は`InMemoryLogStore`の初期化時に指定する
- `maximumEntryCount`が0の場合、記録状態が有効でもログは保持しない
- 保持上限や索引が必要な別実装は、同じ`LogStore`契約で提供できる
