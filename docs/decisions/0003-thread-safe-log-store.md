# スレッド安全なログ保存機能

## 背景

従来の`Logger`は`MainActor`上でログと画面用の索引を直接保持していた。
そのため、ネットワーク処理やバックグラウンドタスクから記録するには
メインアクターへの切り替えが必要で、ログ画面ごとに保存先を分離できなかった。

一方、既存の`Logger.shared.add`は同期APIとして利用されている。
互換性を保ちながら、並行する追加、一時停止、削除の順序を明確にする必要がある。

## 決定

`LogViewerCore`に次の責務を置く。

- `LogStore`: 保存、制御、スナップショット、変更通知の`Sendable`な契約
- `InMemoryLogStore`: `Mutex`で状態変更を同期する標準実装
- `LogStoreSnapshot`: 保存済みログと記録状態の読み取り専用値
- `Logger`: 既存の記録APIを`LogStore`へ転送する`Sendable`な窓口

`InMemoryLogStore`の追加、一時停止、再開、削除は、同じロック上で
直列化される。先に確定した操作の結果が後の操作から見える。

- 一時停止が追加より先なら、そのログは破棄する
- 追加が一時停止より先なら、そのログは保持する
- 削除より前に確定したログは削除する
- 削除より後に確定したログは保持する

変更通知には、現在値から始まる
`AsyncStream<LogStoreSnapshot>`を使用する。
`LogViewerUI`はMainActor上の`LogViewState`で通知を受け取り、
SwiftUIへ読み取り状態を公開する。

ログ画面の`logViewer`修飾子は`LogStore`を受け取る。
引数を省略した場合は`Logger.shared.store`を使用し、
同じ保存機能を明示的に渡せば画面単位の依存性注入として利用できる。

## 採用理由

- 既存の同期`Logger.shared.add`を維持できる
- 呼び出し元を特定のアクターへ強制しない
- 保存状態とSwiftUIのMainActor境界を分離できる
- プロトコルを通してテストやアプリごとの保存実装へ差し替えられる
- 小規模なパッケージに必要な境界だけを追加できる

## 採用しなかった方式

- `actor`の保存実装:
  既存の同期APIから呼ぶには`await`への破壊的変更か、
  順序を保証しにくい非同期転送が必要になるため採用しない。
- `Logger`自体を`@Observable`な共有状態にする方式:
  任意の実行環境からの変更とSwiftUIのMainActor境界が再び結合するため
  採用しない。
- Domain、Interactor、RootCompositionまで分割する方式:
  現在の保存処理には業務フローや外部データ源がなく、
  ターゲットと抽象化が過剰になるため採用しない。

## 影響

- `Logger`は保存状態を直接持たず、`LogStore`へ処理を委譲する
- 共有利用と注入利用は同じ保存契約を使用する
- 画面用のタグと発生元グループはスナップショットから導出する
- 保持件数や索引の性能最適化は、保存契約を維持したまま後続で扱える
